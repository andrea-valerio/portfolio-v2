# iOS 26 Liquid Glass Status Bar — Project Conventions

## Mental model (60 seconds)

iOS 26 Safari renders the system status bar and the floating bottom URL bar as **Liquid Glass** — translucent + lightly blurred — and **samples page content** to derive their tint. Safari 26 **ignores `<meta name="theme-color">`** for this purpose.

Two distinct sampling phases at the **top** edge:

- **At scroll = 0**: Safari samples `position: fixed` / `position: sticky` elements at the viewport top (≈4px deep, ≥80% wide, ≥3px tall).
- **During scroll**: Safari re-samples a composite that includes the **document's actual top-edge content**. A solid fixed navbar alone is NOT enough — dark/contrasty page content scrolling under the top zone can bleed through.

The **bottom** URL bar samples the area **above** its own floating position — i.e., the bottom of the page's scrollable content, NOT the safe-area-inset-bottom zone where the home indicator sits. So a fixed strip at the very bottom of the viewport doesn't actually control the URL bar's tint; whatever page content (or fixed full-viewport overlay) is just above the URL bar's floating position is what gets sampled.

You cannot disable Liquid Glass from web. The design strategy is asymmetric on **two** axes:

- **Top zone**: cover with a fixed cream/theme shield so iOS samples a known surface. We DO control this.
- **Bottom zone**: leave uncovered. Let iOS sample whatever page content (or modal overlay) is naturally there. We DON'T try to control it — attempts to do so were either ineffective or introduced visual bugs (see "What previously failed").
- **Sticky-nav presence**: only on desktop/tablet (≥640px). On phones (<640px) the `.nav` is non-sticky (`position: relative`) and scrolls away with the page. Reason: a fixed nav on iOS WebKit had to live on its own compositor layer (`transform: translate3d(0, var(--vv-offset, 0px), 0); will-change: transform`) to compensate visual-viewport drift, and that layer cached its painted background — silently breaking the cream/dark strip's response to theme toggles. The mobile nav gives that up so the only element pinned to the top safe area is the shield, which is in the main paint tree and re-paints reliably on every `data-mode` flip.

**Critical caveat — the cache**. iOS 26 Liquid Glass caches the sampled tint and only re-evaluates on **user-initiated scroll** or **full page reload**. Programmatic scroll (`window.scrollTo`, any `behavior:`), display-toggle twitches, CSS variable mutations, theme-color meta updates, synthetic events — none of these reliably trigger re-sampling. This is a confirmed iOS 26.x platform limitation, independently reported by Pavel Larionov, Ben Frain, and Jahir Fiquitiva. **Do not attempt to nudge Liquid Glass programmatically** — two attempts in this codebase (commits `f13eca5` scroll twitch, `cff4842` display-toggle twitch) have failed on real-device testing. Accepted limitations:

- Theme toggle (light↔dark) does NOT update the iOS status bar tint mid-session — only on next user scroll or reload.
- Modal open/close does NOT update the iOS bottom URL bar tint mid-session — only on next user scroll or reload.

## Nav appearance matrix

The `.nav` is solid `var(--paper)` everywhere — the four-layer cascade (transparent desktop / iOS-WebKit safety net / Safari frosted-blur) was simplified out in commit `50522da` because the visual difference wasn't worth the cascade-order brittleness. Today the only axis that varies is **stickiness**, and it varies by viewport width, not by browser.

| Surface | `.nav` position | Compositor-promoting transform? |
|---|---|---|
| iPhone Safari portrait (<640px) | `relative` (in document flow, scrolls away) | no |
| iPhone Chrome portrait (<640px) | `relative` | no |
| iPhone landscape (≥640px) | `fixed top:0` | yes (`--vv-offset` translate3d) |
| iPad Safari (any input mode) | `fixed top:0` | yes |
| Android Chrome portrait (<640px) | `relative` | no |
| Desktop Chrome / Firefox / Safari macOS | `fixed top:0` | yes |

The `<640px` ↔ `≥640px` switch is driven by the `.nav.nav--mobile` rule in globals.css; the matching JS hook is `MOBILE_NAV_MQ = "(max-width: 639px)"` in Nav.tsx (which also drives the hamburger / drawer layout). Keep them in lockstep — change one, change both.

Why mobile is non-sticky on phones specifically: a fixed nav on iOS WebKit had to live on its own compositor layer (the visual-viewport-drift `transform` + `will-change`), and that layer cached its painted background and silently broke the `data-mode`-driven cream/dark strip the user actually wants. By dropping `position: fixed` on phones we remove the nav from the iOS Liquid Glass sampling tug-of-war entirely; the only element pinned at the top safe-area zone is `.ios-status-shield`, which lives in the main paint tree and re-paints on every theme flip. Trade-off: phone users lose the always-visible toggle / hamburger / CTA and have to scroll up to use them — accepted in exchange for end-to-end working dynamic theme updates.

## Do's

- ✅ Keep `.nav` solid `var(--paper)` everywhere. Single layer; no per-surface variants. Visual differences come from the **stickiness** axis (fixed on ≥640px, relative on <640px via `.nav.nav--mobile`), not from background variants.
- ✅ Keep the `.nav.nav--mobile { position: relative; transform: none; will-change: auto }` override scoped to the same `(max-width: 639px)` breakpoint that Nav.tsx's `MOBILE_NAV_MQ` uses for the hamburger toggle. If you change one breakpoint, change both — they're conceptually the same "phone-class viewport" notion.
- ✅ Keep `.ios-status-shield` visible on iOS/iPadOS by sizing it directly with `height: env(safe-area-inset-top, 0px)`. `pointer-events: none` so the iOS "tap status bar to scroll to top" gesture still works. The shield naturally collapses to height 0 on desktop, Android, and any device without a top safe-area inset — no visible cream stripe where there's no Liquid Glass to feed. Avoid `@supports (-webkit-touch-callout: none)` for sizing the shield: it has a known iOS 26.1+ regression that can make the shield collapse on iOS too (see Apple Developer Forums thread 808606). Plain `env()` is universally supported and produces the right value per surface.
- ✅ Keep the shield ABOVE `.grain::before` (z=102 > z=100) so the multiply-blend grain can't darken the sample surface.
- ✅ Keep `viewportFit: "cover"` in the viewport export.
- ✅ When adding any new full-viewport overlay (`position: fixed; inset: 0`), mask its blend modes away from both safe-area zones — copy the 5-stop pattern from `.grain::before`.
- ✅ Use `display: none` to remove an element from Liquid Glass sampling. `opacity: 0` and `pointer-events: none` do **not** exclude an element from sampling.
- ✅ Change colors via `--paper` / `--ink` in `:root` and `[data-mode="dark"]` only — themes propagate. Accept that the iOS status bar tint won't update mid-session on theme toggle (it updates on next user scroll).
- ✅ For `.ios-status-shield` specifically, **also** keep an explicit `[data-mode="dark"] .ios-status-shield { background: #161310 }` override alongside the `:root` cascade. The shield is the only element where the user-visible strip color lives or dies based on whether the cascade actually re-paints, so we duplicate the dark target as a literal hex so iOS has a non-variable rule it can't miss. If `--paper` ever drifts away from `#f4ede0` / `#161310`, update the shield rules in lockstep.
- ✅ For modal overlays, use `position: fixed; inset: 0` so they reach the bottom edge — that's how the iOS URL bar gets the dark tint when a modal is open.

## Don'ts

- ❌ **Don't make `.nav` `position: fixed` on phones (<640px).** Pinning it back to the top forces the visual-viewport-drift `transform` + `will-change` back on, which forces the nav onto its own iOS WebKit compositor layer, which caches the painted background and silently breaks the cream/dark strip's response to theme toggles. The whole reason the mobile nav is non-sticky is to keep iOS Liquid Glass from sampling a compositor-cached fixed element. If a future design genuinely needs a sticky mobile nav, expect to re-derive the dynamic-theme-update problem from scratch.
- ❌ Don't make `.nav` semi-transparent by default (e.g., `color-mix(... 60%, transparent)`). Page content will bleed through during scroll on the desktop fixed nav.
- ❌ Don't add a `backdrop-filter` to `.nav` on iOS — Liquid Glass then samples a blurred composite of content behind the nav.
- ❌ Don't put a dark high-contrast element (e.g., `.btn` with `var(--ink)` background) directly below the navbar with no scroll buffer. When the user scrolls and that element reaches the top zone, Liquid Glass picks it up and tints the status bar with it. Either use `.btn.ghost` (transparent + dark border) for in-page CTAs near the top, or push them below ~100px of cream content. **This was the round-2 symptom that motivated `.ios-status-shield`.**
- ❌ Don't reintroduce a `.ios-toolbar-fill-bottom` shield (or any fixed strip in the safe-area-inset-bottom zone) without first revisiting whether you actually need to control URL-bar tint. The answer is usually no — the URL bar samples the area above its floating position, not the safe-area zone, so a bottom shield wouldn't even affect its tint. Removing the bottom shield (this is what we did) lets modal overlays naturally tint the URL bar dark when open. **This was the round-3 simplification.**
- ❌ Don't `display: none` the top shield to "let an overlay through." The shield is unconditional cream/theme — that's the deliberate design. If you need an overlay to visually extend through the top safe area, redesign the overlay (e.g., side panel that doesn't try to span the top), don't kill the shield.
- ❌ Don't add a `backdrop-filter` or `mix-blend-mode` to elements that overlap the shield's z-zone — they'd composite into the sample.
- ❌ Don't put a second fixed element at `top: 0` with a different color — competing sampling targets create unpredictable tint.
- ❌ Don't trust `<meta name="theme-color">` to drive Safari 26's status bar color. Keep the existing media-query variants in the viewport export only for older iOS / Android Chrome / PWA fallbacks.
- ❌ Don't apply `background-clip: content-box` to `.nav` — its background MUST extend through `padding-top: max(18px, env(safe-area-inset-top))` so the safe-area zone is covered.
- ❌ Don't bump the shield z-index above modals (z=100 is your modal/lightbox baseline) without re-thinking the stack. The shield IS at z=102, above modals — that's intentional now (top shield is unconditional). If you ever need a modal to cover the shield, redesign the modal to not span the top safe area.
- ❌ **Don't try to programmatically invalidate the Liquid Glass tint cache.** Two prior attempts (1px scroll twitch in `f13eca5`, display-toggle twitch in `cff4842`) failed on real-device testing on iOS 26.x. Multiple dev reports (Pavel Larionov, Ben Frain, Jahir Fiquitiva) confirm there's no JS technique that works. The accepted limitations are: (a) theme toggle's iOS tint update lags until next user scroll, (b) modal-open URL bar tint update lags until next user scroll. Document these limitations; don't try to fix them.
- ❌ Don't re-add the `:is([data-menu-open], [data-contact-open]) .ios-status-shield { display: none }` rule from commit `5943ed8`. It was an intermediate step — the new pragmatic design (commit after this skill) keeps the top shield unconditional and removes the bottom shield instead.
- ❌ **Don't promote `.ios-status-shield` to its own compositor layer.** No `transform`, no `will-change: transform`, no `backdrop-filter`, no `filter`, no `perspective`, no `translateZ(0)`. iOS WebKit caches the layer's painted background and stops re-rasterizing on `data-mode` flips, so the cream/dark strip gets stuck at whatever theme was active when the page loaded — defeating the entire point of the shield. This was the regression introduced in `51f50ce` (compositor hint for Chrome iOS URL-bar collapse) + `f62a2f4` (re-used the same compositor hint as the carrier for `--vv-offset` visual-viewport drift compensation). The fix is to leave the shield off the compositor and let `html, body { background: var(--paper) }` paint the same color through any transient drift gap (cream-on-cream / dark-on-dark, visually invisible). The visual-viewport drift compensation stays on `.nav` only — that's where the drift is actually noticeable because the nav has structured content (logo + buttons) instead of a flat color bar.
- ❌ Don't switch the shield's `background` back to `var(--paper)` alone. Keep the explicit `[data-mode="dark"] .ios-status-shield { background: #161310 }` override paired with the literal `#f4ede0` default. The literal pair gives iOS WebKit a target it can paint reliably even if a future change accidentally re-promotes the shield to its own layer (which would silently break the cascade-based update again, harder to spot in review).

## Modify checklist (when changing this area)

1. Open `src/app/globals.css` and locate the four pieces: `.nav` (desktop fixed) + `.nav.nav--mobile` (mobile relative override), `.ios-status-shield` (literal-hex light + dark), `#projects, #publications` scroll-margin-top (mobile override), `.grain::before` mask.
2. Open `src/app/layout.tsx` — confirm the `viewport` export and the single shield div (top only, no bottom).
3. Open `src/components/chrome/Nav.tsx` — confirm `MOBILE_NAV_MQ` is still `(max-width: 639px)`. If you change it here, also change the `.nav.nav--mobile` rule's effective scope and the `#projects, #publications` mobile media query in globals.css.
4. If colors are changing: edit `--paper` / `--ink` in `:root` and `[data-mode="dark"]` only **and** mirror the new dark color literally in the `[data-mode="dark"] .ios-status-shield` rule.
5. If adding or removing a fixed element near `top: 0`: keep exactly **one** solid sampling target at the top edge (the shield) — don't stack competing ones with different colors. On phones, that means the only `position: fixed; top: 0` element should be `.ios-status-shield`.
6. If you genuinely need a sticky mobile nav, expect to re-derive the dynamic-theme-update problem from scratch (see the failure history for the saga 51f50ce → f62a2f4 → fix → "no it didn't work" → mobile-nav-non-sticky pivot).
7. If adding a new full-viewport overlay: ensure it uses `position: fixed; inset: 0` (so it covers the bottom edge for iOS URL bar sampling), and consider whether its open-state needs a CSS hook on `<html>` — the existing `data-menu-open` / `data-contact-open` pattern is the precedent.
8. If adding a new fullscreen overlay with blend modes (`mix-blend-mode`, `backdrop-filter`): mask it away from both safe-area zones using the `.grain::before` pattern.

## State-driven appearance and accepted iOS limitations

iOS 26 Liquid Glass caches its tint sample and only re-evaluates on user-initiated scroll or full reload. There is **no working JS technique** to invalidate this cache. The codebase's accepted limitations:

- **Theme toggle** (light↔dark via `applyMode()` in `Nav.tsx`): updates `data-mode` and re-cascades all `var(--paper)` / `var(--ink)` backgrounds correctly, including the visible `.ios-status-shield` cream/dark strip — which flips immediately in the same frame as the toggle (the literal-hex dark override + no-compositor-layer rules above are what make this synchronous). The iOS Liquid Glass system status bar tint above the strip, however, still lags — it stays at the previous theme's tint until the user scrolls. So right after a toggle, the user briefly sees the new theme's strip color but the previous theme's iOS chrome tint sitting on top of it. Documented in the inline comment in `applyMode()` and in the shield's own block comment.

- **Modal open/close** (`menuOpen` useEffect in `Nav.tsx`, `open` useEffect in `ContactModal.tsx`): toggles `data-menu-open` / `data-contact-open` on `<html>`. The iOS bottom URL bar tint will lag — it stays at the previous sample (page content) until the user scrolls. In practice, most users scroll inside the open modal panel within a second or two, which triggers the re-sample, so the lag is usually invisible.

- **`data-menu-open` / `data-contact-open` attributes**: kept as state-tracking primitives even though no CSS rule currently consumes them. Cheap to maintain; useful CSS hooks if a future feature needs modal-state-driven styling.

**Don't** add nudges, twitches, or any JS that tries to force Liquid Glass to re-sample. Two attempts have failed; the iOS limitation is genuinely a platform constraint, not a problem we haven't worked hard enough to solve.

## Verification (after each change)

1. **Real iPhone with notch / Dynamic Island on iOS 26.x.** Simulators do NOT render Liquid Glass identically. Connect via USB and use Mac Safari → Develop → [iPhone] → [tab] for the inspector — that's the real iPhone Safari, not Mac Safari with iPhone UA spoofing.
2. **No-modal scroll**: scroll past the H1 hero title. Status bar zone should stay a clean cream/theme tint — no recognizable page content (text, buttons) showing through.
3. **Theme toggle (iPhone notched portrait, the case the user actually cares about)**: tap the sun/moon. The CSS updates immediately (DevTools shows `data-mode="dark"` and `--paper: #161310`). The visible `.ios-status-shield` strip — a ~44–50px tall band at the very top of the viewport — must flip color **immediately** in the same frame as the toggle (cream → dark or dark → cream). If the strip is stuck at the previous theme's color until the next scroll or reload, something has re-promoted a top-edge sample target to its own compositor layer and broken the cascade — check (a) `.ios-status-shield` for stray `transform`, `will-change`, `backdrop-filter`, `filter`, etc., AND (b) the `.nav.nav--mobile` override for any regression that put the mobile nav back to `position: fixed` (which would re-introduce the same compositor-cache problem one level up). The iOS Liquid Glass system tint above the strip still lags one frame behind the strip until next user scroll; that lag is the platform-level cache and is **expected** — document, don't fix. Only the strip itself must update synchronously.

3b. **Mobile nav stickiness check**: scroll down on an iPhone (or Mac DevTools narrow ≤639px viewport). The nav must scroll away with the page — it should NOT remain pinned at the top. If it stays pinned, the `.nav.nav--mobile` override has been broken and the iOS theme-toggle regression in step 3 is about to come back. Hash-navigate to `#projects` from the hamburger menu to confirm the section lands flush below the iOS status bar zone (no 88px gap above) — the `@media (max-width: 639px)` `scroll-margin-top` override is what makes that work.
4. **Mobile menu open**: tap the hamburger. Top safe-area zone stays cream/theme (intentional — top shield is unconditional). Bottom URL bar zone: should eventually tint dark to match the modal overlay; the first frame may still show the previous sample. Scroll inside the menu panel to confirm the dark tint kicks in. Close — bottom should revert to page-content tint at next scroll.
5. **Contact modal open** (via "Get in touch" CTA, both desktop and mobile): same expectations as the mobile menu — top stays cream/theme, bottom eventually tints dark.
6. **Rotate landscape**: `env(safe-area-inset-top)` becomes 0; the `max(4px, ...)` floor keeps the shield sample-eligible.
7. **Tap the iOS status bar to scroll-to-top**. Should still work — the shield has `pointer-events: none` so the tap passes through.
8. **Open desktop Safari / Chrome / Firefox**: frosted nav (Safari macOS) or transparent nav (Chrome/Firefox) per the four-layer cascade. **No cream stripe at the very top** — the shield's height is `env(safe-area-inset-top, 0px)`, which naturally resolves to 0 on desktop where there's no safe-area inset. There is also no matching stripe at the bottom (deliberate — no bottom shield).

Lost the iOS-landscape / non-notch 4px floor that was previously documented as sample-eligibility insurance — accepted trade-off, those modes are edge cases and the iOS Liquid Glass cache already lags theme/modal updates regardless. **Working state for the theme-driven cream/dark strip on iOS** until the next two commits broke it again.
- **Commit `51f50ce`** — added `transform: translateZ(0); will-change: transform` to `.ios-status-shield` (and `.nav`), motivated by Chrome iOS URL-bar collapse layout shake — "forces a dedicated compositor layer so the shield doesn't reflow during Chrome iOS's URL-bar collapse". **Regression on iOS WebKit (Safari + WKWebView)**: promoting the shield to its own compositor layer caused iOS to cache the layer's painted background and stop re-rasterizing on `data-mode` flips. The cream/dark strip went stuck at whatever theme was active when the page loaded. The iOS Liquid Glass system tint already had this cache problem (documented limitation), but the SHIELD STRIP itself had been updating synchronously via `var(--paper)` cascade — until this commit silently broke that too. Symptom is identical to the eb4062a regression from a user's perspective ("the bg area of the status bar doesn't change color with the theme anymore"), so easy to misdiagnose as the same `@supports` collapse.
- **Commit `f62a2f4`** — repurposed the same compositor hint as the carrier for `--vv-offset` (`transform: translate3d(0, var(--vv-offset, 0px), 0)`) to counter iOS 26's visual-viewport drift bug (WebKit Bugzilla 297779) on the shield and the nav. Did NOT cause the regression (that was already there from `51f50ce`) but cemented it — the transform now had a "real" reason to exist, making it tempting for a future agent to keep it. The drift compensation is genuinely useful on `.nav` (structured content where shake is visible) but moot on `.ios-status-shield` (a flat-color bar where the body's `var(--paper)` background paints the same color through any transient gap).
- **Intermediate commit** — dropped `transform` and `will-change` from `.ios-status-shield` entirely (kept them on `.nav`). Switched the shield's `background` from a single `var(--paper)` rule to two literal-hex rules — `background: #f4ede0` default + `[data-mode="dark"] .ios-status-shield { background: #161310 }` override — to give iOS WebKit a non-variable target. Plausible theory; **failed on real-device testing** anyway. User came back with: "No it didn't work" + selected "I never see a cream/dark strip at all — that zone shows page content, the iOS Liquid Glass blur of page content, or nothing dedicated". The shield-only fix wasn't enough because the `.nav` was still pinned at `top: 0` with the visual-viewport-drift transform/will-change, still owned its own iOS WebKit compositor layer, and that layer's painted background at the safe-area zone was still being sampled by Liquid Glass and still cached — making the visible "strip" essentially the nav's stale paint, not the shield's correctly-updating paint. Lesson: if **any** element competing for the top safe-area Liquid Glass sample target is on a compositor layer, the cache problem doesn't go away no matter how clean the shield's own setup is.
- **Current commit** — pivots to making the `.nav` itself non-sticky on phone-class viewports (<640px) via a `.nav.nav--mobile { position: relative; transform: none; will-change: auto; top/left/right/z-index: auto }` override that piggybacks on the existing `nav--mobile` class set by Nav.tsx. Mobile-only override; desktop / tablet still use `position: fixed` + the `--vv-offset` transform (where the shake is genuinely visible and the iOS WebKit compositor cache problem doesn't apply because there's no notched safe-area on those surfaces in the same way). With the nav out of the document's top-edge sticky pile-up on phones, the only element pinned at `top: 0` in the safe-area zone is `.ios-status-shield` — main paint tree, literal-hex colors, no compositor — and Liquid Glass samples it cleanly. User-visible result: the cream/dark strip flips immediately on theme toggle on iPhone Safari portrait. Trade-off: the mobile nav's toggle / hamburger / CTA scroll away with the page; users have to scroll back up to access them. Accepted by the user explicitly: "New solutions: just make the navbar non-sticky at the top on mobile." Also reduced `#projects, #publications` `scroll-margin-top` to `env(safe-area-inset-top, 0px)` on the same mobile media query so hash-navigation lands flush below the iOS status bar zone instead of leaving 88px of empty space (the 88px was sized for the now-absent fixed nav). Verification step 3 rewritten to check both the strip-flip AND the mobile-nav-scrolls-away behavior, so a future regression of either shape is caught at first real-device test.

**Three conditions must all hold on iOS 26.x for the top status bar tint:**

1. A fixed sampling target near `top: 0` with a solid theme-driven background. (`.ios-status-shield` — literal `#f4ede0` light + `[data-mode="dark"] { #161310 }` dark, **never** `var(--paper)` alone, **never** on a compositor layer.)
2. Nothing above it (overlays, blend modes) darkens it in the safe-area zone.
3. Page content scrolling under the top zone doesn't have dark, high-contrast elements within ~100px of the navbar bottom edge — or those elements use a low-contrast variant (e.g., `.btn.ghost`).

**Two conditions must all hold for the visible shield strip itself to flip color synchronously on theme toggle (independent of iOS Liquid Glass tint, which has its own cache):**

1. The shield's `background` is set both via the light-mode literal and an explicit `[data-mode="dark"]` literal override (not just a `var(--paper)` cascade rule).
2. The shield does NOT own its own compositor layer — no `transform`, `will-change`, `backdrop-filter`, `filter`, `perspective`, or any other property that promotes it. iOS WebKit caches compositor layers' painted backgrounds and silently breaks the cascade-driven update.

**For the bottom URL bar**, no conditions to enforce — let iOS sample whatever's naturally there (page content, or modal overlay when one is open).
